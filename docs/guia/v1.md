# Guía técnica · API v1

Cómo envía sus datos operacionales el sistema de una empresa, o el conector que lo lee: ventas,
inventario, órdenes de compra en tránsito y órdenes de producción en curso. La API es la misma
para todos los clientes y habla en términos de planificación, no de ningún ERP.

| | |
|---|---|
| Contrato | `1.0.0-draft` · [OpenAPI 3.1](../referencia.md) |
| Formato | JSON · UTF-8 |
| Errores | `application/problem+json` (RFC 9457) |

!!! note "Datos de ejemplo"
    Todos los ejemplos usan una empresa ficticia, *Acme*, con ubicaciones `CD01` (centro de
    distribución), `T001` y `T002` (tiendas) y SKUs inventados.

## Estado { #estado }

El contrato completo está publicado. En el ambiente de pruebas funciona **el ciclo completo de
ventas**: abrir, enviar, probar, confirmar y consultar, más la frescura por fuente. Inventario,
órdenes de compra y órdenes de producción vienen después; mientras tanto esas rutas responden
`501`.

| Ruta | Para qué | Estado |
|---|---|---|
| `GET /v1/meta` | Ubicaciones, unidades y base del valor de la empresa | En pruebas |
| `POST /v1/ingest/batches` | Abre un lote | En pruebas · ventas |
| `POST /v1/ingest/batches/{id}/parts` | Envía líneas | En pruebas · ventas |
| `POST /v1/ingest/batches/{id}/dry-run` | Valida y calcula la diferencia sin aplicar | En pruebas · ventas |
| `GET /v1/ingest/batches/{id}` | Estado, conteos y cuarentena | En pruebas |
| `GET /v1/ingest/batches` | Historial de lotes | En pruebas |
| `POST /v1/ingest/batches/{id}/commit` | Valida y aplica | En pruebas · ventas |
| `POST /v1/ingest/{entidad}` | Atajo de una llamada para lotes chicos | En pruebas · ventas |
| `GET /v1/data-health` | Frescura por fuente y ubicación | En pruebas |
| Inventario, OC, OP | Lotes de las otras tres entidades | Después de ventas |

## Ambientes y clave

Cada empresa recibe una **clave de API por ambiente**, junto con la dirección de ese ambiente. La
empresa sale de la clave, nunca del cuerpo del request. SOMA guarda solo una huella de la clave:
si se pierde, se emite otra.

| Ambiente | Prefijo | Uso |
|---|---|---|
| Pruebas | `soma_test_…` | Desarrollo y certificación del conector. No toca el plan real |
| Producción | `soma_live_…` | Solo después de certificar el conector |

```http
Authorization: Bearer soma_test_••••••••
SOMA-Connector: acme-erp/1.4.0
Content-Type: application/json
```

`SOMA-Connector` identifica quién envía y en qué versión. Es opcional y recomendado: queda
registrado en cada lote.

| Alcance de la clave | Permite |
|---|---|
| `ingest:sales` | Lotes de ventas |
| `ingest:inventory` | Lotes de inventario |
| `ingest:purchase_orders` | Lotes de órdenes de compra |
| `ingest:production_orders` | Lotes de órdenes de producción |
| `read:health` | `/v1/data-health` |

Sin clave, o con una clave inválida o revocada: `401 unauthorized`. Con una clave válida sin el
alcance de esa entidad: `403 forbidden_scope`. `/v1/meta` y la consulta de lotes aceptan
cualquier clave válida de la empresa.

## El lote

Todo se envía en lotes. Un lote declara una entidad y un alcance, recibe las líneas en una o
varias partes, y se aplica completo o no se aplica. Reenviar un lote o una parte con el mismo
contenido no duplica nada.

### 1. Abrir el lote

El `batch_id` lo genera el cliente: de 8 a 100 caracteres de `A-Z a-z 0-9 . _ : -`. El mismo
`batch_id` con el mismo encabezado devuelve el mismo lote; con otro encabezado,
`409 batch_id_conflict`.

```http
POST /v1/ingest/batches
```

```json
{
  "batch_id": "ventas-2026W45-0001",
  "entity": "sales",
  "source_system": "ERP · ventas diarias",
  "extracted_at": "2026-11-09T02:00:00-04:00",
  "scope": {
    "date_from": "2026-10-12",
    "date_to": "2026-11-08",
    "locations": ["CD01", "T001"]
  },
  "value_basis": "net",
  "expected_lines": 18342,
  "partition_counts": [
    { "location": "CD01", "lines": 9120 },
    { "location": "T001", "lines": 9222 }
  ]
}
```

Respuesta `201`:

```json
{
  "batch_id": "ventas-2026W45-0001",
  "entity": "sales",
  "status": "open",
  "api_version": "1.0.0-draft",
  "connector": "acme-erp/1.4.0",
  "created_at": "2026-11-09T06:00:04Z",
  "expected_lines": 18342,
  "lines_received": 0,
  "lines_quarantined": 0,
  "diff": null,
  "problem_code": null
}
```

- `extracted_at` lleva zona horaria y es el momento en que se leyó la fuente.
- `partition_counts` es opcional. Si viene, tiene que sumar `expected_lines`, y SOMA compara cada
  partición (ubicación, o ubicación y día) con lo que recibió. Así se detecta una lectura
  truncada.

### 2. Enviar las partes

Hasta 10.000 líneas y 5 MB por parte, numeradas desde 1. Reenviar la misma parte con el mismo
contenido no suma dos veces; con otro contenido, `409 batch_id_conflict`.

```http
POST /v1/ingest/batches/ventas-2026W45-0001/parts
```

```json
{
  "part_number": 1,
  "lines": [
    { "location": "T001", "sku": "CAM-AZ-M", "date": "2026-10-14",
      "movement": "sale", "quantity": 24, "value_usd": 180.00 },
    { "location": "T001", "sku": "CAM-AZ-M", "date": "2026-10-15",
      "movement": "return", "quantity": 2, "value_usd": 15.00,
      "original_sale_date": "2026-10-14" }
  ]
}
```

Respuesta `200`:

```json
{
  "batch_id": "ventas-2026W45-0001",
  "part_number": 1,
  "lines_received": 10000,
  "total_lines_received": 10000
}
```

Las líneas no se rechazan al recibir la parte: se validan una por una en el `dry-run` y en el
`commit`. Un `422` solo puede venir del encabezado del lote o de la parte, nunca de una línea.

### 3. Probar sin aplicar (`dry-run`)

Valida todo y compara el lote con lo que SOMA tiene dentro del alcance. No escribe nada y se
puede repetir. Es la herramienta principal para poner en marcha un conector.

```http
POST /v1/ingest/batches/ventas-2026W45-0001/dry-run
```

Respuesta `200`:

```json
{
  "batch_id": "ventas-2026W45-0001",
  "would_status": "held",
  "diff": {
    "inserted": 12, "updated": 40, "deleted": 2,
    "unchanged": 6150, "deleted_value_usd": 31.50
  },
  "lines_quarantined": 1,
  "problem_code": "first_batch_review",
  "problems": ["first_batch_review"],
  "problem_detail": "first_batch_review: 6192 filas del alcance vinieron de cargas por archivo…",
  "unmatched": { "locations": 0, "skus": 3 },
  "quarantine_sample": [
    { "line": 418, "part": 1, "field": "quantity",
      "code": "non_positive_quantity", "message": "Input should be greater than 0" }
  ]
}
```

- `would_status` es el estado que tendría el lote si se confirmara.
- `problems` lista todos los códigos encontrados, del más grave al menos grave; `problem_code`
  es el primero.
- `unmatched` cuenta los SKUs y las ubicaciones que SOMA no conoce.
- `quarantine_sample` trae hasta 100 líneas apartadas.

### 4. Confirmar (`commit`)

```http
POST /v1/ingest/batches/ventas-2026W45-0001/commit
```

Cierra el lote (`open` → `validating`) y responde **`202`** de inmediato con el estado del lote.
En segundo plano SOMA valida todo, calcula la diferencia contra lo que tiene dentro del alcance y
escribe **solo lo que cambió**: el resultado se consulta en el paso 5.

- **De a uno.** Los commits de una misma empresa y entidad se procesan en orden, nunca dos a la vez.
- **Espera al plan.** Si la empresa tiene un cálculo de plan en curso, el lote espera a que
  termine (sigue en `validating`) y se aplica después, para no cambiar los datos a mitad de
  cálculo. El detalle del lote dice qué está esperando.
- **Pausas de SOMA.** Si la base de SOMA no acepta escrituras por un momento, el lote se
  reintenta solo. El conector no tiene que hacer nada.
- **Retenido.** Si el lote queda `held`, se libera desde la revisión de datos de SOMA y se aplica
  sin reenviarlo.

#### Atajo de una llamada

Para lotes chicos (hasta 10.000 líneas), `POST /v1/ingest/sales` recibe encabezado y líneas en
un solo cuerpo, y abre, carga y confirma de una vez. Responde `202` igual que el `commit`.
Reenviar el mismo cuerpo con el mismo `batch_id` devuelve el estado del lote ya confirmado, sin
duplicar.

### 5. Consultar el resultado

`GET /v1/ingest/batches/{id}` devuelve el mismo objeto que al abrir, con el estado, la
diferencia, los conteos, el problema si lo hubo y una muestra de la cuarentena. Un estado que el
conector no conoce se trata como "todavía no terminado".

`GET /v1/ingest/batches?entity=sales&status=held&since=2026-11-01T00:00:00Z&limit=50` lista los
lotes del más nuevo al más viejo. Si hay más, la respuesta trae `next_cursor`, que se pasa como
`cursor`.

## Frescura de los datos (`/v1/data-health`)

Dice, por fuente y ubicación, hasta qué fecha tiene SOMA datos y si están al día. Requiere el
alcance `read:health`. Sirve para que el conector o el equipo de la empresa vean una ubicación que
dejó de enviar antes de que el plan salga corto.

```http
GET /v1/data-health
```

```json
{
  "as_of": "2026-11-10T08:00:00Z",
  "sources": [
    { "entity": "sales", "location_code": "T001", "last_cut": "2026-11-08",
      "age_periods": 0, "state": "fresh", "last_batch_id": "ventas-2026W45-0001" },
    { "entity": "sales", "location_code": "T002", "last_cut": "2026-10-25",
      "age_periods": 2, "state": "late", "last_batch_id": "ventas-2026W43-0001" }
  ],
  "runs_blocked": false,
  "blocking_reasons": []
}
```

| `state` | Significado |
|---|---|
| `fresh` | Al día |
| `late` | Sin datos nuevos desde hace 2 períodos (valor inicial, ajustable por empresa). Solo avisa |
| `stale` | Sin datos nuevos desde hace 3 períodos o más. Aviso fuerte |
| `missing` | SOMA no tiene datos de esa fuente y ubicación |

`runs_blocked: true` significa que ningún cálculo de plan de la empresa puede correr hasta
resolver lo que dice `blocking_reasons`. Por ejemplo, `unknown_location`: llegó una ubicación que
la empresa todavía no definió.

## Alcance y completitud

!!! warning "Dentro del alcance declarado, lo que no viene cuenta como cero"
    Cero venta, cero stock, ninguna orden abierta. Fuera del alcance SOMA no toca nada. Por eso
    el conector tiene que leer su fuente completa antes de enviar, y abortar si no puede
    comprobarlo.

| Entidad | Alcance | Ejemplo |
|---|---|---|
| Ventas | Ventana de fechas × ubicaciones | `{"date_from": "2026-10-12", "date_to": "2026-11-08", "locations": ["CD01"]}` |
| Inventario, OC, OP | Fecha de corte × ubicaciones | `{"as_of": "2026-11-09", "locations": ["CD01", "T001"], "empty_locations": []}` |

- **Reenvío de ventas.** Cada envío semanal repite las últimas cuatro semanas (valor inicial,
  ajustable por empresa), para recoger las correcciones tardías del ERP.
- **Fecha de corte.** La define el conector según cómo lee la fuente. Un conector que consulta
  los lunes a las 02:00 puede enviar `as_of` = ese lunes y las ventas hasta el domingo. SOMA la
  guarda tal cual.
- **Ubicación declarada sin líneas** (inventario, OC, OP): rechaza el lote, salvo que esté en
  `empty_locations`. En ventas es solo un aviso, porque los cierres y feriados son normales.
- **Lote viejo.** Si `extracted_at` es anterior al del último lote aplicado sobre el mismo
  alcance, el lote se rechaza con `batch_stale`.
- **Fuente al día, no solo completa.** Que el conector lea todas las filas de un día no prueba que
  la fuente ya tenga ese día: un día vacío de una fuente atrasada parece un día sin ventas, y
  dentro del alcance cuenta como cero. El conector envía solo los períodos que su fuente ya
  cubre: por ejemplo, la fuente se sincronizó después del cierre y su último dato llega al último
  día hábil del período. Si no puede comprobarlo, no envía ese período.
- **Carga inicial.** Para reemplazar historia cargada por archivo, conviene enviar lotes de
  varias semanas (por ejemplo, un trimestre): cada lote sobre datos de archivo se revisa una vez
  (`first_batch_review`), y con lotes grandes la revisión es por trimestre y no por semana.

## Líneas

Las líneas son estrictas: un campo que no existe (`qty` en lugar de `quantity`) es un error, no
un dato que se ignora. Fechas en `YYYY-MM-DD`.

### Ventas · `sales`

| Campo | Tipo | | Notas |
|---|---|---|---|
| `location` | string | obligatorio | `location_code` o `client_code` de SOMA |
| `sku` | string ≤ 100 | obligatorio | Código del cliente |
| `date` | date | obligatorio | Día del movimiento |
| `movement` | `sale` \| `return` | obligatorio | La devolución se indica aquí, no con signo |
| `quantity` | number > 0 | obligatorio | Siempre positiva |
| `value_usd` | number ≥ 0 | obligatorio | Sin IVA; bruto o neto según la empresa |
| `uom` | string | opcional | Sin `uom` = unidad base del SKU |
| `lost_sales_qty` | number ≥ 0 | opcional | Venta perdida |
| `original_sale_date` | date | opcional | Solo en `return`; no posterior a `date` |
| `document_ref` | string ≤ 100 | opcional | Trazabilidad; no forma parte de la identidad |

### Inventario · `inventory`

| Campo | Tipo | | Notas |
|---|---|---|---|
| `location` | string | obligatorio | |
| `sku` | string ≤ 100 | obligatorio | |
| `quantity_on_hand` | number ≥ 0 | obligatorio | Disponible: sin comprometido ni cuarentena |
| `uom` | string | opcional | |
| `value_usd` | number ≥ 0 | opcional | |
| `lot`, `exp_date` | string, date | opcional | Juntos, para productos que vencen. Sin ellos, no vence |

### Órdenes de compra en tránsito · `purchase_orders`

| Campo | Tipo | | Notas |
|---|---|---|---|
| `location` | string | obligatorio | Destino |
| `po_number`, `line_ref` | string ≤ 100 | obligatorio | Orden y línea |
| `sku` | string ≤ 100 | obligatorio | |
| `quantity_pending` | number > 0 | obligatorio | Pedido menos recibido |
| `expected_date` | date | obligatorio | Llegada esperada |
| `uom`, `supplier_code`, `order_date` | | opcional | |
| `soma_ref` | string | opcional | La aprobación de SOMA que originó la orden, para no contarla dos veces |

### Órdenes de producción en curso · `production_orders`

| Campo | Tipo | | Notas |
|---|---|---|---|
| `location` | string | obligatorio | Planta |
| `order_ref`, `sku` | string ≤ 100 | obligatorio | |
| `quantity_pending` | number > 0 | obligatorio | Planificado menos producido |
| `expected_completion_date` | date | obligatorio | |
| `status` | `released` \| `in_progress` | obligatorio | |
| `uom`, `soma_ref` | | opcional | |

No se envían órdenes en borrador, canceladas ni anuladas. Una orden que se cancela deja de venir
y, por la regla de completitud, sale de SOMA.

### Grano: cuándo dos líneas son la misma

| Entidad | Clave | Líneas con la misma clave |
|---|---|---|
| Ventas | ubicación, SKU, fecha, movimiento, fecha original | Se suman, ya en unidad base. Da igual enviar líneas de factura o ya agregadas |
| Inventario | ubicación, SKU, lote, vencimiento | Se suman |
| OC | ubicación, `po_number`, `line_ref`, SKU | La segunda va a cuarentena (`duplicate_key`) |
| OP | ubicación, `order_ref`, SKU | La segunda va a cuarentena (`duplicate_key`) |

SOMA guarda las ventas como una cifra neta por ubicación, SKU y día: ventas menos devoluciones,
con lo devuelto registrado aparte. Al comparar, las cantidades se redondean a 4 decimales y los
dólares a 2. Una diferencia menor cuenta como "sin cambio".

## Códigos, unidades y valor

`GET /v1/meta` devuelve lo que el conector necesita para validar antes de enviar:

```json
{
  "api_version": "1.0.0-draft",
  "period_unit": "W",
  "value_basis": null,
  "locations": [
    { "location_code": "CD01", "client_code": "ALM-CENTRAL", "name": "Centro de distribución" },
    { "location_code": "T001", "client_code": "TDA-NORTE", "name": "Tienda Norte" }
  ],
  "uom_conversions": [ { "uom": "DOC", "factor": 12, "sku": null } ]
}
```

- **Unidad de período** de la empresa: `D`, `W` o `M`.
- **Ubicaciones.** Se aceptan el código de SOMA o el del cliente. Una ubicación que SOMA no
  conoce no es error: sus líneas se guardan y el lote queda retenido (`unknown_location`) hasta
  que la empresa la defina. Mientras tanto no corre ningún motor de la empresa.
- **SKU.** Se envía el código del cliente. Un SKU sin ficha entra igual y se informa en
  `unmatched.skus`. Los alias y los códigos ignorados se configuran una vez por empresa, no
  viajan en cada envío.
- **Unidades.** Cada SKU tiene una unidad base, la más fina que se mueve. Con `uom`, SOMA
  convierte con el factor del SKU o, si no hay, con el de la empresa (`sku: null`). Una unidad
  sin conversión va a cuarentena (`unknown_uom`). Códigos en mayúsculas: `DOC`, `KG`, `GAL`.
- **Valor.** Siempre en dólares y sin IVA. Bruto o neto de descuentos lo decide la empresa una
  vez (`value_basis: null` = todavía sin declarar). El primer lote de ventas que trae
  `value_basis` lo fija. Sin declarar en ningún lado, el lote se rechaza
  (`value_basis_undeclared`); distinto al de la empresa, `value_basis_mismatch`.

## Validación y estados

| Nivel | Qué pasa | Ejemplos |
|---|---|---|
| Línea | Va a cuarentena con su motivo; el resto del lote sigue | Fecha inválida, cantidad cero, campo mal escrito, unidad desconocida |
| Lote: rechazo | No se aplica nada y SOMA conserva los datos anteriores | Conteos que no calzan, línea fuera del alcance, cuarentena sobre el 1%, lote viejo |
| Lote: retención | Espera una decisión de la empresa en la revisión de datos; al liberarlo se aplica sin reenviar | Ubicación desconocida, borraría más de lo normal, llegó mucho menos de lo esperado, primer lote sobre datos cargados por archivo |

| Estado | Significado |
|---|---|
| `open` | Recibiendo partes |
| `validating` | Confirmado, procesándose |
| `applied` | Aplicado completo |
| `applied_with_quarantine` | Aplicado; algunas líneas apartadas |
| `held` | Retenido para revisión |
| `rejected` | Rechazado; nada cambió. También un retenido que se descartó en la revisión o que reemplazó un lote más nuevo (`batch_discarded`) |
| `expired` | Abierto más de 24 h sin confirmar |

!!! warning "Protección contra borrados"
    Antes de aplicar, SOMA calcula cuánto borraría el lote dentro de su alcance. Si supera el
    umbral de la empresa (valores iniciales: 2% de las filas o 0,5% del valor), el lote queda
    retenido con `deletion_guard_tripped` y el detalle de lo que borraría.

!!! warning "Volumen anómalo"
    Si una semana completa de un lote de ventas trae menos del 15% de lo esperado (el plan
    aprobado, la misma semana del año anterior o el promedio de las últimas 8 semanas), el lote
    queda retenido con `volume_anomaly`: casi nada llegó, y probablemente el conector no leyó todo.

Los códigos de error de cada nivel están en el [catálogo de errores](../errores.md).

## Límites

| Límite | Valor | Al pasarlo |
|---|---|---|
| Líneas por parte | 10.000 | `413 payload_too_large` |
| Tamaño de una parte | 5 MB | `413 payload_too_large` |
| Requests por clave | 60 por minuto | `429 rate_limited` con `Retry-After` |
| Lote abierto sin confirmar | 24 horas | `410 batch_expired` |
| Historial por página | 1 a 200 (50 por omisión) | `422` |

Son valores iniciales y pueden subir. Una carga inicial grande (cientos de miles de líneas) se
envía en lotes de muchas partes. Un trimestre de ventas diarias de una cadena de tiendas, con unas
250.000 líneas, cabe en un lote.

## Reintentos

Abrir, enviar partes y confirmar son **idempotentes**: repetir la misma llamada con el mismo
`batch_id` (y el mismo número de parte) no duplica nada. Por eso reintentar siempre es seguro.

| Respuesta | Qué hace el conector |
|---|---|
| `429 rate_limited` | Espera `Retry-After` y reintenta |
| `503 service_unavailable` | SOMA no acepta escrituras por un momento (mantenimiento, ampliación de disco, reinicio). Espera `Retry-After` y reintenta la misma llamada; hasta unos 10 minutos es normal |
| Otro `5xx` o error de red | Reintenta unas pocas veces con espera creciente; si sigue, avisa |
| `401`, `403`, `404`, `409`, `410`, `413`, `422` | No reintenta igual: corrige o consulta el estado |

## Versionado

- **La versión mayor va en la URL:** `/v1/…`.
- **Dentro de v1 solo se agrega:** rutas nuevas, campos opcionales de entrada, campos nuevos en
  las respuestas, valores nuevos en enums de respuesta y códigos de error nuevos.
- **Lector tolerante.** El conector ignora los campos que no conoce en las respuestas, trata un
  estado de lote desconocido como "todavía no terminado" y un código desconocido como error
  genérico de su nivel.
- **Qué es un cambio que rompe:** quitar o renombrar un campo, volver obligatorio uno opcional,
  cambiar tipo, unidad o significado, cambiar un código de error o una regla de completitud o
  de diferencia. Eso es una `/v2`, aunque el JSON quede igual.
- **Convivencia.** v1 y v2 funcionan juntas al menos seis meses. Durante ese tiempo v1 responde
  con los headers `Deprecation` y `Sunset`, este último con la fecha de apagado.
- **Trazabilidad.** Cada lote guarda la versión de la API con que llegó y el header
  `SOMA-Connector`.
- **Changelog y releases.** Cada cambio del contrato queda en el [changelog](../changelog.md) y
  cada versión es un [release](https://github.com/SomaEngine/soma-api-docs/releases) con sus
  notas.

## Certificar un conector

Antes de recibir la clave de producción, el conector pasa por el ambiente de pruebas:

- [ ] Lee `/v1/meta` y valida localmente ubicaciones y unidades antes de enviar.
- [ ] Comprueba que leyó la fuente completa (conteos por día o por ubicación) y aborta si no
      puede comprobarlo. Envía `partition_counts`.
- [ ] Comprueba que la fuente ya cubre cada período que envía, y no envía los que no puede
      comprobar.
- [ ] Genera un `batch_id` único por envío y lo reutiliza solo al reintentar ese mismo envío.
